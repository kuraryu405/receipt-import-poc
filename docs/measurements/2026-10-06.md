# 初期計測・確認結果（2026-10-06）

## 概要

公開データセット JaWildText の `receipt_kie` 実画像で、Gemini APIによる構造化抽出と画面表示を確認した。5件の簡易評価では3件成功・2件APIエラーとなり、その後の失敗サンプル1件の再確認では429を検出して中断した。

この記録は初期の動作確認であり、業務利用時の精度や処理性能を判断するには件数が不足している。

初回の5件評価と、SDKのエラー分類・自動再試行の修正後の再確認は条件が異なる。両者を同一条件の測定として合算しない。

社内レシートや未公開の購入情報は使用していない。画像、個別の参照値・予測値、APIキー、上流エラー本文はこの記録に含めない。

## 1. ブラウザーでの実画像E2E

公開レシート画像1枚について、ファイル選択 → プレビュー → 解析中表示 → 結果・明細表示 → 生JSONの展開を確認した。生JSONを解釈できることも確認した。

### 処理時間・トークン数

| 計測項目 | 実測値 |
| --- | ---: |
| サーバー側の解析処理時間 | 43,675 ms（約43.7秒） |
| SDKの入力トークン数 | 1,356 |
| SDKの出力トークン数 | 422 |

`processingTimeMs` は `analyzeReceiptImage` の開始から、Geminiの応答取得・JSON解釈・Zod検証を完了するまでの時間。ブラウザーからのアップロードや描画を含む操作全体の所要時間ではない。

トークン数はSDKのusageをそのまま記録した。入力と出力の単純和は1,778であり、SDKが返した合計2,702とは一致しない。この差の内訳は確認していない。料金の実測も行っていない。

1件のみの計測なので、平均・中央値・p95・最大値や、ウォームアップ、通信状況による差は評価できない。CLI評価の各件の処理時間・トークン数は集計レポートに保存されていない。

## 2. 先頭5件の簡易精度評価

### 対象と実行方法

`receipt_kie` の `train` 先頭5件（`offset=0`, `limit=5`）を評価スクリプトで逐次処理した。無作為抽出ではない。

同じ対象範囲を評価するコマンドは以下。APIの利用枠を確認してから実行すること。現行実装はエラー分類と自動再試行を修正済みのため、初回と同一の失敗処理にはならない。

```sh
npm run evaluate:jawildtext -- --limit 5 --offset 0 --report ./eval-report.json
```

現在のスクリプトの既定値は、接続先 `http://localhost:3100`、リクエスト間の待ち時間1,000ms。初回実行での待ち時間オプションは別途記録していない。

### APIの取得結果

| 状態 | 件数 |
| --- | ---: |
| 構造化応答取得・検証成功（`processed`） | 3 |
| APIエラー（`failed`） | 2 |
| スキップ（`skipped`） | 0 |
| 対象 | 5 |

構造化応答の取得成功割合は3/5（60%）。これはAPI呼び出しを含む今回の取得結果であり、OCR精度ではない。初回の2件の失敗はエラー分類修正前に502として扱われたため、上流の失敗原因は特定できない。2件ともレート制限だったとは判断しない。

### 項目別の正規化後の完全一致

APIエラーの2件は採点から除外されている。以下は成功した3件のうち、参照値を採点可能な項目だけを分母にした指標。

| 項目 | 一致数 / 採点数 | 一致率 |
| --- | ---: | ---: |
| 店舗名 | 2 / 3 | 66.67% |
| 取引日 | 3 / 3 | 100% |
| 合計金額 | 3 / 3 | 100% |
| 消費税額 | 3 / 3 | 100% |

採点方法は次のとおり。

- 店舗名：Unicode NFKC正規化と空白除去後の完全一致。空の参照値は除外する。
- 取引日：スクリプトが解釈できる年・月・日表記を `YYYY-MM-DD` に揃えて一致判定する。解釈できない参照値は除外する。
- 金額：参照値の通貨記号・桁区切り・空白を除いて数値化し、予測された数値と一致判定する。数値化できない参照値は除外する。
- 小計、支払方法、登録番号、明細の数量・単価はこの項目別指標では評価していない。

### 明細の簡易指標

品名＋金額ペアを多重集合として照合する。品名はNFKC正規化・空白除去を行い、金額が採点可能なペアだけを扱う。数量・単価・行順は照合しない。

| 項目 | 値 |
| --- | ---: |
| TP（一致したペア） | 9 |
| FP（余分な予測ペア） | 1 |
| FN（取得できなかった参照ペア） | 1 |
| Precision | 0.90 |
| Recall | 0.90 |
| F1 | 0.90 |

これはJaWildText論文の正式なKIE F1評価手順の再現ではない。APIエラーの除外、先頭5件という偏り、正規化による差の吸収を考慮する必要がある。個別の予測値を保存していないため、この集計だけでは店舗名の不一致や明細のFP/FNの具体的な原因は分からない。

集計の原本：[evaluation-summary.json](./2026-10-06/evaluation-summary.json)。

## 3. SDKエラー分類修正後の再確認

Interactions APIの内部エラーは、公開 `ApiError` クラスに対する `instanceof` では判別できず、利用制限などが汎用502になっていた。数値の `status` / `statusCode` を安全に読む方式へ修正し、SDKの自動再試行を無効化した（`maxRetries: 0`、タイムアウト180秒）。

修正後、初回評価で失敗したサンプル1件（`offset=2`, `limit=1`）を再確認した。

| 確認項目 | 結果 |
| --- | --- |
| API応答 | HTTP 429（利用制限） |
| CLI動作 | 即時中断、終了コード3 |
| 自動再試行 | なし |
| この実行の採点対象 | 0件 |

集計の原本：[sdk-check-summary.json](./2026-10-06/sdk-check-summary.json)。このJSONでは `model: "unknown"`、`processed: 0`、`failed: 0` となっている。429による中断が通常の失敗件数へ加算される前に処理されるためであり、APIエラーがなかったことを意味しない。成功応答がないためモデル名もレポートに入らない。

### レート制限について確認できたこと

- 無料枠のプロジェクトで429を受けたことは確認できた。
- 分あたりのリクエスト数、分あたりのトークン数、日あたりのリクエスト数のどれが原因かは未確認。上流エラー本文や再試行時刻は保存していない。
- AI Studioでは利用状況がまだ表示されておらず、具体的な上限・消費量は確認できなかった。
- [公式のレート制限説明](https://ai.google.dev/gemini-api/docs/rate-limits)では、日次リクエスト枠は米国太平洋時間の午前0時にリセットされる。2026年10月6日の時差では日本時間16時に相当する。これは日次枠の説明であり、今回の解除時刻を確定する情報ではない。
- 解除後に実APIを再実行して成功するかは、この記録時点では未確認。

## 5. 次の計測で残す情報

1. 429の対象制限と実際の復旧をAI Studioと単発リクエストで確認する。
2. 実行時刻・コミット・モデル・サンプル範囲・リクエスト間隔・再試行設定を実行単位で残す。
3. API成功率と、成功応答の項目別精度を別々に集計する。
4. 各件の処理時間・usageを個別情報なしで記録し、件数を増やして中央値やp95を算出する。
5. 店舗名・明細の不一致を、表記揺れ・読み取り誤り・対象項目の取り違えなどに分類する。
6. サンプルを広げ、8%/10%の混在、税込/税抜、預り金/お釣り、登録番号、画像品質の違いを評価する。
